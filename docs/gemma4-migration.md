# Gemma 4 MLX migration runbook

This document records the Gemma 4 migration from the `adrgrondin/mlx-swift-lm`
fork to the official `ml-explore/mlx-swift-lm` upstream, and provides the
procedure for future `mlx-swift-lm` bumps.

## Timeline

| Date | Event |
| --- | --- |
| 2026-04-12 | LiteRT backend removed on `main`. `HitokuInference` started depending on `adrgrondin/mlx-swift-lm@c21a372` to get pre-merge Gemma 4 VLM support. |
| 2026-04-12 | Gemma 4 generation found broken on fork: `[broadcast_shapes] Shapes (64) and (79) cannot be broadcast` in the repetition-penalty processor during generation. |
| 2026-04-15 | Upstream PR [#180](https://github.com/ml-explore/mlx-swift-lm/pull/180) ("Add Gemma 4 model (text, vision, MoE)") merged into `ml-explore/mlx-swift-lm`. Follow-up fixes landed through commit `2dccb38`. |
| 2026-04-16 | This migration: dependency swapped to official upstream at exact commit `2dccb380cd26822589af6ec8682132b7149a425b`. |

## What changed in this migration

Two files modified, one regenerated, one deleted:

1. **`HitokuInference/Package.swift`**
   - Dependency URL: `https://github.com/adrgrondin/mlx-swift-lm` → `https://github.com/ml-explore/mlx-swift-lm`
   - Revision: `c21a372` → `2dccb380cd26822589af6ec8682132b7149a425b` (full SHA for reproducibility)
   - Added a policy comment at the top describing the pinning strategy and bumping procedure.

2. **`project.yml`** (`packages.mlx-swift-lm` entry)
   - Same URL + revision change.
   - Inline comment documenting why we do not revert to the fork.

3. **`HitokuDraft.xcodeproj`** — regenerated via `xcodegen generate`.

4. **`HitokuDraft.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`** — deleted, then regenerated by Xcode during the next resolve. Xcode writes it now to `~/Library/Developer/Xcode/DerivedData/HitokuDraft-*/SourcePackages/workspace-state.json` under the workspace-state format.

## What did NOT change

Intentionally byte-identical across the migration:

- `HitokuInference/Sources/HitokuInference/*` (all core protocol files)
- `HitokuInference/Sources/MLXBackend/MLXInferenceBackend.swift`
- `VoiceEditor/Services/ModelManager.swift` — including the factory-selection logic `useVLM = model.isVLM && visionEnabled`
- `VoiceEditor/Models/ModelFamily.swift` — including `Gemma4ModelFamily` sampling (temperature 0.5, topP 0.9, repetition penalty 1.2) and thinking-block regex
- `VoiceEditor/Models/ModelOption.swift` — including the Gemma 4 entries in `bundledDefaults`
- `VoiceEditor/Services/ConversationCoordinator.swift` — no changes to multi-turn logic

**Rationale:** upstream at `2dccb38` exposes the same `MLXLLM` / `MLXVLM` /
`MLXLMCommon` products with the same `Tokenizer`, `Downloader`, `TokenizerLoader`,
and `GenerateParameters` signatures as the fork at `c21a372` did. The
`TokenizerBridge` and `HubDownloaderBridge` in `ModelManager.swift` compile
unmodified against upstream. Verified by building `HitokuInference` in isolation
(`cd HitokuInference && swift build`) and then the app target
(`xcodebuild -project HitokuDraft.xcodeproj -scheme HitokuDraft build`).

## Smoke tests (run before committing or bumping)

These must all pass on a local build before a commit merges or a version ships.

### 1. Qwen 3.5 — regression guard (highest priority)

Qwen 3.5 perf and behavior must be byte-identical before/after.

- [ ] Load **Qwen 3.5 4B 4-bit** with "Allow vision" **off** in Settings → Advanced.
  - Should load via `LLMModelFactory` (check Xcode debug console for no VLM references during load).
  - Voice edit: "Rewrite more formally: I gotta go" → clean paste, no thinking blocks.
  - Token/sec should match pre-migration numbers.
- [ ] Load Qwen 3.5 4B with "Allow vision" **on**, Advanced context enabled, Safari window focused.
  - Should load via `VLMModelFactory`.
  - Voice edit: "Summarize this page" → coherent answer referencing screenshot content.

### 2. Gemma 4 E2B — unblocked by this migration

- [ ] Load **Gemma 4 E2B 4-bit** with "Allow vision" **off**.
  - Should load via `LLMModelFactory` (weight sanitization strips vision tower).
  - Voice edit: "Summarize this in one sentence: [short paragraph]" →
    - completes without `broadcast_shapes` throw,
    - stops cleanly at `<end_of_turn>`,
    - no `<|channel>thought…<channel|>` residue in the overlay or paste.
- [ ] Enable "Allow vision", screenshot a Safari article, voice edit "What is this about".
  - Should load via `VLMModelFactory`, complete without `Gemma4Error.imageTokenCountMismatch`.

### 3. Gemma 4 E4B (larger variant)

- [ ] Repeat test #2 with **Gemma 4 E4B 4-bit**. Confirms model-size scaling.

### 4. Model switch stability

- [ ] In Settings → Model, switch **Qwen 3.5 → Gemma 4 E2B → Qwen 3.5**. Verify:
  - No leaked RAM (Activity Monitor: memory should return to baseline after each switch).
  - Status indicator returns to "Ready" after each load.
  - No residual "mlx" backend registered without a container (internal invariant).

### 5. Auto-offload

- [ ] Enable auto-offload in Settings → General.
- [ ] Load Gemma 4, idle for 5 minutes. Confirm the model is unloaded (RAM drops, "Status: Not Set Up").
- [ ] Press Ctrl+Z to trigger a voice edit. Model reloads cleanly from cache within a few seconds.

### 6. Multi-turn voice edit

- [ ] Voice edit a paragraph with Gemma 4. Verify output.
- [ ] Without reselecting text, do a second Ctrl+Z with a follow-up instruction ("make it shorter"). Verify the coordinator uses `lastEditContext` and the second edit refines the first.

If any of these fail → file an issue, revert the migration (see below), or
file upstream in `ml-explore/mlx-swift-lm`.

## Rollback procedure

If Gemma 4 generation regresses vs. the fork, or Qwen 3.5 breaks:

```bash
# 1. Revert Package.swift and project.yml
#    (either `git revert <migration-commit>` or hand-edit)
# 2. Regenerate Xcode project
xcodegen generate
# 3. Purge cached resolution
rm -f HitokuDraft.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved
rm -rf HitokuInference/.build
rm -rf ~/Library/Developer/Xcode/DerivedData/HitokuDraft-*
# 4. Rebuild
cd HitokuInference && swift build && cd ..
xcodebuild -project HitokuDraft.xcodeproj -scheme HitokuDraft build
```

If reverting to the fork, accept that `broadcast_shapes` crashes can occur on
Gemma 4 generation until a new upstream fix is merged and we re-migrate.

## Bumping `mlx-swift-lm` to a newer upstream commit

Follow this procedure every time. Do not skip steps.

1. **Pick the new commit.** Read the upstream commit log; verify that no
   regression PR landed since the current pin. Prefer commits that ship a
   reviewed fix, not WIPs.
2. **Update two files** with the exact 40-char SHA:
   - `HitokuInference/Package.swift` (the `revision:` string)
   - `project.yml` (`packages.mlx-swift-lm.revision`)
3. **Regenerate and clean:**
   ```bash
   xcodegen generate
   rm -f HitokuDraft.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved
   rm -rf HitokuInference/.build
   ```
4. **Build in isolation first:** `cd HitokuInference && swift build`. If this
   fails, the upstream API drifted — fix the bridges in `ModelManager.swift`
   (`TokenizerBridge`, `HubDownloaderBridge`, `HubTokenizerLoaderBridge`) and
   `MLXInferenceBackend.swift` before touching Xcode.
5. **Build the app:** `xcodebuild -project HitokuDraft.xcodeproj -scheme HitokuDraft build`.
6. **Run the smoke tests above.** All six must pass.
7. **Commit with a message** that names the commit and quotes the relevant
   upstream PR / commit title. Update this runbook's Timeline table.

## Why we still use an exact commit, not a tag range

Upstream has not cut a stable release tag that covers Gemma 4 + tool calling
+ audio together. Tag ranges (`.upToNextMinor(from: "3.31.3")`) would pull
untested commits between upstream stabilization rounds. Exact commits mean
every Hitoku Draft build is bit-for-bit reproducible against a single
upstream checkpoint.

Switch to a tag range once upstream cuts a tag that:
1. Covers all Gemma 4 use cases we care about (text + vision).
2. Has been validated by at least one other downstream consumer
   (`mlx-vlm`, `mlx-lm`, or the LMStudio team).
3. Passes our six smoke tests.
